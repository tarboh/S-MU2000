# MAME に返せそうなもの

移植の過程で見つけたもののうち、**上流の MAME でも同じことが起きるはず**の
ものを溜めておく。送ったものは印を付ける。

送り済み: [mamedev/mame#16075](https://github.com/mamedev/mame/pull/16075)
（SWP30 のループ長マスクとピッチ clamp。README の「上流への還元」）

---

## 1. デバイスの状態に初期値が無い（swp30 / sh7042 まわり）

**症状**: 同じ ROM・同じ入力でも、実行ごとに出る音が変わることがある。

`swp30_device` の per-channel の構造体（`streaming_block` `filter_block`
`iir1_block` `envelope_block` `lfo_block`）と、`sh_port16/32_device` の
`m_dr` / `m_io` などに初期値が書かれていない。firmware がそれらを書く前に
読む経路があり、**そこに直前まで別のものが置いていた値がそのまま出る**。

こちらでは、起動時の引数のパス区切りを `\` から `/` に変えるだけで
（長さも中身も他は同じ）音が変わるところまで絞れた。CRT が起動時に置いた
文字列が、初期化していない要素の上に残っていたため。reset 直後の状態を
丸ごと突き合わせると 28 バイト違い、初期値を書いたら 0 バイトになった。

**直し方**: 宣言に初期値を書く。per-channel の配列は
`std::array<streaming_block, 0x40> m_streaming = {};` のように丸ごと
0 で初期化すれば、中の要素を 1 つずつ触らずに済む。

**MAME 側での見え方**: MAME は save state を持つので「セーブして読み直すと
音が変わる」形でも出るはず。デバッガで走らせたときと素で走らせたときの
違いとしても出る可能性がある。

こちらのコミット: `2c02e0c`

## 2. CMT が、割り込みを出さないときも予定を入れている

**症状**: MU 系のドライバで CPU が細切れにされ、速度が出ない。

`sh_cmt_device::internal_update()` は、コンペアマッチの時刻を必ず
「次の予定」として返す。MU2000 の firmware は CMT を **COR=1・1/8** で
走らせていて、合わせは **16 サイクルごと**に起きる。この速さで割り込みは
処理できないので、firmware は割り込みを切ってカウンタを細かい時間の
物差しとして読んでいるだけ。

それでも予定に入るので、スケジューラは 16 サイクルごとに CPU を止めて
周辺全部に予定を聞き直す。こちらで数えたら、「次の予定」を出したものの
**99.8%（2440 万回）が CMT** で、CPU は 1 サンプル（635 サイクル）のあいだに
**80 回**止められていた。

**直し方**: 割り込みを出す設定（CMCSR の CMIE）でないチャンネルは、予定に
入れない。カウンタと合わせの印は、読まれたときに計算すれば同じ値になる
（`cmcnt_r` は元から `cnt_update()` を呼んでいる。`cmcsr_r` にも同じ
追いつきを入れる）。

**効き目**: こちらでは CPU の時間が **46% 減った**（実行ループが 1 サンプル
あたり 80.5 周 → 1.5 周、実時間比 58% → 38%）。MAME でも MU 系の速度に
そのまま効くはず。

**注意**: 命令の切れ目が動くので、発音の時刻が最大 1 サンプルずれる。
こちらでは声の中身（サンプル番地・ピッチ・形式）は完全に同じままだった。

こちらのコミット: `sh_cmt.cpp` / `sh_cmt.h`

## 3. 直流が MEG から出ている（調べただけ。直していない）

**症状**: 出力に、鳴っている音の量に比例した直流が乗る。実機は乗らない。

こちらの実測では 30Hz 以下が 5.3% 残っていた（実機 0.13%）。順に潰した結果:

* ミキサの丸め（`mixer_att`）ではない。最近接・0 方向に変えても 0.3% も動かない
* 声ごとのフィルタでもない
* **声の出口は直流を持っていない**（1 声を 1 秒ぶん測って平均 −0.175、最大 1470）
* **MEG の出口が持っている**。ミキサへ入る `m_m[0x20]` / `m_m[0x21]` の平均が
  +354（最大 2667）で、出力の 13% が直流
* エフェクトの送りを 0 にすると、尾の直流が +4.96 → −0.016 になる

MEG の中では `meg_pack24()` の `p >> 15`（床丸め）が軽い曲では半分を説明する
が、重い曲では動かない。残りは振幅に比例するので、掛け算側の非対称
（`m1_expand`、飽和、リバーブ RAM の詰め方）が疑わしい。

くわしくは [doc/todo.md](todo.md) の 3 番。

## 4. 声ごとのピッチ LFO の速さと中心（直した）

**症状**: ビブラートレートを上げると、速くなるはずのビブラートが遅くゆっくり
揺れる。伸ばした音の音程が狂って聞こえる
（[tarboh/S-MU2000#1](https://github.com/tarboh/S-MU2000/issues/1)、FF7 の Still More Fighting の矩形波リード）。

`lfo_block`（レジスタ `cccccc 001010`）に 2 つ間違いがあった。

* **step は 6 ビット**。MAME は `(data >> 8) & 0x1f` で 5 ビットしか取らない。
  firmware はビブラートレートが 72 を超えると 6 ビット目（bit 13）を立てる
  （レートを 0-127 で振って書き込みを見た: 76 で `0x6654` = step 38）。
  落とすと step 6 になり、6.4Hz のはずが 1Hz になる
* **揺れの中心は 0x800**。MAME は `(m_state - 0x400) * depth >> 11`。state は
  0-0xfff なので、これだと半分の振れ幅ぶん高い側に寄り、振れ幅も 2 倍になる。
  `(m_state - 0x800) * depth >> 12`（粗いほうは `>> 9`）で実機と合う

実機（MU2000EX、S/PDIF で録音）との比べ。PC80、2 秒の音、CC1=127:

| レート | 実機 | 直す前 | 直した後 |
|---|---|---|---|
| 64 | 5.32 Hz ±40c 中心 -7c | 5.23 Hz ±76c +39c | 5.23 Hz ±39c -9c |
| 76 | 6.43 Hz ±39c | 1.06 Hz ±93c +54c | 6.41 Hz ±38c -9c |
| 104 | 8.97 Hz ±33c | 3.55 Hz ±84c | 8.92 Hz ±33c |
| 127 | 10.62 Hz ±35c | 5.26 Hz ±79c | 10.65 Hz ±30c |

試験の MIDI は `tools` ではなく手で作った（レート 56〜127 を 2 秒ずつ）。
こちらのコミット: `swp30.cpp` の `lfo_block::type_step_pitch_w` と `get_pitch`

## 5. ミキサーの減衰の下 4 ビット（直した）

**症状**: パンを動かすと、音量が値によって行ったり来たりする。振り切っても鳴っている
側が大きくならない。曲のバランスが実機と違う
（[tarboh/S-MU2000#1](https://github.com/tarboh/S-MU2000/issues/1)）。

`mixer_att` の 4.4 形式の下 4 ビットは **32 分の 1 刻み**。MAME は

    (sample - ((sample * (att & 0xf)) >> 4)) >> (att >> 4)

と 16 分の 1 にしている。これだと `0x18`（0.5 × 1/2）と `0x20`（1/4）が同じ大きさに
なり、段の途中が次の段より小さくなる。`>> 5` にすると、1 から 17/32 まで下がって
次の段（1/2）へほぼ滑らかにつながる。

firmware がパンごとに書く値（左 / 右、スロットの減衰 0x18 を足す前）:
パン 1 = `00/ff`、8 = `00/39`、16 = `00/27`、24 = `01/1d`、32 = `02/17`、40 = `03/12`、
48 = `04/0e`、56 = `06/0b`、64 = `08/08`。

実機（MU2000EX、S/PDIF で録音）で 17 段のパンを測り、中央からの差を比べた
（PC80 と PC16、リバーブ・コーラスは 0）:

| パン | 実機 L / R | 直す前 | 直した後 |
|---|---|---|---|
| 8 | +3.6 / -18.5 | +0.0 / -18.7 | +3.5 / -18.4 |
| 16 | +3.6 / -11.6 | -0.0 / -30.3 | +3.5 / -11.5 |
| 32 | +2.8 / -5.5 | -2.5 / -24.2 | +2.8 / -5.5 |
| 56 | +1.0 / -0.9 | -12.1 / -1.8 | +1.0 / -0.9 |

エフェクトの送りと戻りも同じ式を通るので、曲全体のバランスも変わる。FF7 の
Still More Fighting を 1 トラックずつ鳴らすと、13 トラック中 11 が実機と ±0.6dB に入った
（直す前は -8〜+5dB）。

こちらのコミット: `swp30.cpp` の `mixer_att`

MAME に投稿した PR（2026-10-02）: [mamedev/mame#16292](https://github.com/mamedev/mame/pull/16292)（ブランチ `swp30-mixer-att`）。MAME でもパンの表が実機と合った（パン 16 で +3.5 / -11.5）。

## 6. 声ごとのフィルタの 2 段目にも 1 段目のレゾナンスが掛かる（直した）

**症状**: オーバードライブギター（PC29）の低い音で、160Hz あたりが実機より 10dB
膨らむ。CC71（Harmonic Content）を上げると差が 20dB まで広がる
（[tarboh/S-MU2000#1](https://github.com/tarboh/S-MU2000/issues/1) の ch13）。

`filter_block` の 2 段は、レゾナンス（`filter_b` の上 5 ビット）を 1 つ共有する。
種類の bit 12 が立っている段（1, 3, 5, 7, 9, b, d, f）だけがそれを使い、
立っていない段は q=1 固定のはず（資料の「with fixed q=1」）。

MAME は `filter_b_w` の時点で **1 段目の種類だけを見て** `m_filter_p2` を決め、
2 段目にもそれを使う。PC29 は 1 段目がレゾナンス付きローパス（`16ee`、b=`8800`）、
2 段目が Q 固定のハイパス（`8280`、約 165Hz）なので、2 段目に強い山ができていた。
b を書いた後に 1 段目の種類が変わったときも、古い値のまま残る。

直し方: `m_filter_p2` には b から計算した値を常に入れ、`step()` で段ごとに
`BIT(m_filter_N_a, 12) ? m_filter_p2 : 0x80` を選ぶ（状態の形は変わらない）。

実機（MU2000EX、S/PDIF）との比べ。PC29、E2、1/3 オクターブ、全体の音量差を引いた値:

| 帯域 | 直す前 | 直した後 |
|---|---|---|
| 126Hz | +7dB | +0 |
| 160Hz | +10dB | +0 |
| 160Hz（CC71=127） | +19dB | +0 |
| 1-6kHz | ±0 | ±0 |

曲では ch13 が +2.4dB → +0.5dB になり、比べた 11 トラックが全部 ±0.5dB に入った。

こちらのコミット: `swp30.cpp` の `filter_block::step` と `filter_b_w`

## 7. 声を取り上げる途中の 1 サンプルで abort() する（直した）

**症状**: 発音数がいっぱいのまま MIDI をたくさん流すと、`streaming_block::read_8c` の
`abort()` で落ちる。MAME の MU100 でも同じように落ちる（利用者の報告）。
報告された値は `m_loop=80005302`、`m_start=40000001`。

`read_8c`（圧縮したサンプル）は、`m_loop` の bit 31（逆向きに鳴らす）が立っていると
`abort()` する。圧縮したサンプルを逆向きに鳴らす声は ROM に無いが、次の場面で一時的にそうなる:

1. 発音数がいっぱいで、firmware が鳴っている声（圧縮したサンプル、エンベロープはまだ動いている）を取り上げる
2. 次の音のレジスタを 1 つずつ書く。スタンダードキットのタム（ノート 47・48・50）は
   **逆向きの 16bit サンプル**（start `40000001`、loop `80005302`、address `00017303`）
3. start と loop を書いたあと、address を書く前に 1 サンプル進むと、前の音の圧縮の address
   （例 `ee41ae06`）と逆向きの印が混ざって `read_8c` に入る

1 回の取り上げで混ざるのは 1 サンプルだけで、次の書き込みとキーオンで正しい状態に戻る。
全パートにいろいろな音色を鳴らしながらタムを連打する MIDI（乱数で 4 通り）で、
1 曲に 0〜4 回起きた。

直し方: 逆向きのときは読まずに、直前の 4 つの値（`m_dpcm_s0`-`s3`）を返す。
実機がその 1 サンプルに何を出すかは分からないが、取り上げられる声なので聞こえる差は無い。
それまで通っていた曲の音は 1 バイトも変わらない（そこに来たら落ちていたので）。

こちらのコミット: `swp30.cpp` の `streaming_block::read_8c`

## 8. リバーブ RAM の clear を無視している（直した）

**症状**: パフォーマンスモードで、パフォーマンスを選ぶのと同時に鍵盤を弾くと、
002 Stereo Grand などが全振幅に張り付いて戻らない（issue #3）。100 のパフォーマンスのうち
002・020・033・036・043・074 で起きた。実機は普通に鳴る。

firmware はエフェクトの種類を替えるたびに、`revram_enable_w` にビットを立ててから
`revram_clear_w` に同じビットを書く（`0002`・`0004`・`0008` のように 1 ビットずつ）。
MAME の `revram_clear_w` は logerror だけで何もしない。消さないと、新しいエフェクトの
プログラムが前のエフェクトの遅延メモリの残りを読み、帰還の網が飽和したまま戻らない。

ビット i は MEG のメモリ地図 `m_map[i]` の区画（先頭 = 下 8 ビット × 1024、長さ =
2 の (10 + ビット 8-10) 乗）と読んだ。マスターとスレーブで地図が違っても、それぞれに合う。

直し方: 書いたビットの区画を、その時点の地図で 0 にする（0 は `revram_decode` で 0）。
100 のパフォーマンスを流し直して張り付きは 0。テストの曲の音は 1 バイトも変わらない。

こちらのコミット: `swp30.cpp` の `revram_clear_w`

## 9. プログラムの最後の 3 命令の書き込みがミキサに届かない（直した）

**症状**: パフォーマンス 017 FeedbackEG と 048 Warm Amp が全く鳴らない（実機は鳴る）。
XG モードでも、バリエーションを TALK MOD にしてインサーションで使うと出力が 0 になる。

m/r レジスタへの書き込みは 3 命令遅れて入る。プログラムの最後の 3 命令（`0x17d`-`0x17f`）が
書いたものは、次のサンプルの `0x000`-`0x002` で入る。ところが `sample_step` のミキサは
その前に m20-m2f の出口を読み、送りを書く。TALK MOD はインサーションの出口 m2c/m2d を
`0x17e`/`0x17f` で書くので:

1. ミキサは出口の新しい値を読めない
2. 次のサンプルの頭で、遅れた書き込みがミキサの送りを出口の古い値で潰す
3. プログラムは送りの代わりに自分の出口（0）を読むので、0 のまま抜け出せない

ヤマハのプログラムがこう書いている以上、実機はサンプルの切れ目で遅れた書き込みが済んでから
ミキサとやり取りするはず（切れ目に空きのクロックがあると見た）。

直し方: `sample_step` の頭で、遅れている m/r/index の書き込みを全部入れて空にする
（`meg_state::flush_writes`）。0x000-0x002 が 0x17d-0x17f の書いたレジスタを読むときだけ
値が 1-3 命令早く見えるが、そう読むプログラムは見ていない。

実機（MU2000EX、S/PDIF）との比べ。和音、オクターブ帯ごとの相対レベル:

| | 直す前 | 直した後 |
|---|---|---|
| 017 FeedbackEG | 無音 | 帯ごとに ±1.6dB、減衰の形も一致 |
| 048 Warm Amp | 無音 | 帯ごとに ±1dB（8kHz 以上を除く）、減衰の形も一致 |

テストの曲の音は 1 バイトも変わらない。

こちらのコミット: `swp30.cpp` の `meg_state::flush_writes` と `sample_step`

## 10. 16bit のサンプルを偶数の位置で読むと、後ろの 2 つが前の 2 つの写しになる（直した）

**症状**: 16bit のサンプルを使う音色（パフォーマンス 012 Old EP など）で、実機に無い
高い倍音と、倍音の間の雑音が乗る。低い倍音は合っている。

`streaming_block::read_16` は補間に使う 4 つの値を読む。位置が奇数のときは 3 つの dword
（`adr`・`adr+1`・`adr+2`）から取るが、偶数のときは 2 つ目の dword も `adr` から読んでいて、
`val2`/`val3` が `val0`/`val1` と同じになる。コメントの図（`bbbbaaaa ddddcccc`）では
2 つ目は次の dword。

直し方: 偶数のときの 2 つ目を `wave.read_dword(adr+1)` にする。

実機（MU2000EX、S/PDIF）との比べ。パフォーマンスモードで 1 音ずつ、全体の音量差を引いた値。
「倍音の差」は -45dB より大きい倍音の食い違いの平均、「床」は倍音の間の雑音の差:

| | 倍音の差 | 床 |
|---|---|---|
| 012 Old EP、ノート 48 | 22.2 → 2.5dB | +18.9 → +6.4dB |
| 012 Old EP、ノート 60 | 21.9 → 4.1dB | +12.4 → +5.6dB |
| 012 Old EP、ノート 72 | 8.6 → 2.4dB | +15.1 → +6.4dB |
| 062 Slap Switch（逆向きの 16bit） | 変わらず | 変わらず |

100 のパフォーマンスを C4 で比べると、012 だけが 12.8dB → 1.1dB（1/3 オクターブ帯の食い違いの
平均）になり、ほかの 99 は 1 バイトも変わらなかった。テストの曲では drums と dense が変わる。

こちらのコミット: `swp30.cpp` の `streaming_block::read_16`

MAME に投稿した PR（2026-10-02）: 12 と一緒に [mamedev/mame#16291](https://github.com/mamedev/mame/pull/16291)（ブランチ `swp30-sample-fetch`）。

## 11. MEG の分岐が無いことになっている（直した）

**症状**: LO-FI を使う音（パフォーマンス 007 Super Bass、097 Lo-Fi Loop）が、実機より
10dB 以上小さく、音色も違う。097 はピッチまで 49 セントずれて聞こえる。

MAME は「384 命令を毎サンプル順に回す（分岐は無い）」としていて、bit 0x3f の立った命令を
ALU の無い命令として読み流している。実際にこの命令が現れるのは、116 種類のエフェクトのうち
LO-FI（7 か所）と DYNA FLT / DYNA FLANG / DYNA PHASE（2 か所ずつ）だけ。
前後の並びから次のように読んだ:

* bit 0x20 の立った命令は、結果（p）が負か、0 かを覚える
* bit 0x3f の立った命令は、bit 0x18-0x1f の条件が合えば、bit 0x10-0x17 の番地
  （同じ 256 番地の中、必ず先）の手前まで、あいだの命令を何もしない命令にする
* 条件: bit 3 が 0 なら必ず。1 なら bit 2 が 1 で負のとき、0 で負でないとき。
  bit 1 が立っていれば 0 のときも

LO-FI では、振幅を ±m19 で止める所（`if (r01 - m19 > 0) r01 = m19; else if (r01 + m19 < 0) r01 = -m19`
の形が L と R に 1 つずつ）と、サンプリング周波数を落とすサンプル＆ホールドの間引き。
DYNA 系では `m01 = max(m01, m02)`（包絡の追従）と `m01 = max(m01, 0)`（整流）。
どれも条件の読みと辻褄が合う。分岐の命令そのものと、飛び越された命令は、レジスタも
メモリも t も触らない（書き込みの遅れの輪は普通に回る）。

直し方: `meg_state::step()` と `run_program()` に上の分岐を入れる。`tools/meg_dis.py` も
`skip to 13d if n`、`flags` のように出すようにした。

実機（MU2000EX、S/PDIF）との比べ。パフォーマンスモードで C4 を 1 音、1/3 オクターブ帯の
食い違いの平均と、音量差（ほかのパフォーマンスはおよそ +12.9dB）:

| | 帯の食い違い | 音量差 | ピッチ |
|---|---|---|---|
| 007 Super Bass（LO-FI） | 7.9 → 0.7dB | -0.6 → +14.1dB | 0 |
| 097 Lo-Fi Loop（LO-FI + 3BAND EQ + COMPRESSOR） | 5.6 → 1.1dB | +3.4 → +12.9dB | -49 → 0 セント |

## 12. 圧縮サンプルのループで、差分を 1 つ落とすことがある（直した）

**症状**: ループの短い圧縮サンプルを高い音で鳴らすと（パフォーマンス 041 Deep Harp の C6）、
倍音は合っているのに、倍音の間に実機に無い線が並ぶ（基音から -39dB、f0 の 1/6 おき）。
声の出力の平均値が数周期おきに段になって動く。

`read_8c` は差分を `m_pos+3` まで積算して 4 つの値を作る。ループの後ろには、先頭の 3 つの
差分の写しが置いてある（ROM で確かめた。12bit のサンプルも同じで、先頭 3 つの写しのあとは 0）。
`streaming_block::step` はループを跨ぐと `m_dpcm_pos = 3`（次に積算する位置）にしている。
1 回に 1 つ進んで跨いだならそれで合うが、ピッチが 1 より上だと時々 2 つ進む。そのときは
先頭の 1 つ目までしか積算していないのに 3 から続けるので、2 つ目の差分を落とし、
積算器がずれたまま残る。ずれは跨ぐたびに溜まる。

直し方: `m_dpcm_pos -= m_loop_size`（積算の済んだ所の続きから）。1 つ進みで跨いだときは
今までと同じ 3 になる。

実機（MU2000EX、S/PDIF）との比べ。041 Deep Harp の C6（c3 形式、ループ 44 サンプル）:

| | 直す前 | 直した後 | 実機 |
|---|---|---|---|
| 1/3 オクターブ帯の食い違いの平均 | 22.7dB | 0.3dB | — |
| 倍音 1 と 2 のあいだの床（基音比） | -57dB（-39dB の線） | -76dB | -75dB |

3 次補間そのものの誤差をこのループで計算すると -74dB で、実機の床と合う。
100 のパフォーマンスを C2・C4・C6 で比べ直し、食い違いが変わったのは 041 の C6 だけ
（ほかは 0.3dB より動かない）。テストの曲では dense が変わり、直流が 172.6 → 18.6、
30Hz 以下の割合が 17.6% → 9.6% になった（60 音を重ねて圧縮サンプルのずれが溜まっていた）。

こちらのコミット: `swp30.cpp` の `streaming_block::step`

MAME に投稿した PR（2026-10-02）: 10 と一緒に [mamedev/mame#16291](https://github.com/mamedev/mame/pull/16291)。MAME の dense で直流 417 → 78、30Hz 以下 12.6% → 0.4%。

## 13. チップの中のピッチ EG（スロット 0x0B・0x10、内部ポート 4）が無い（直した）

**症状**: 一部の XG 音色が 1〜2 オクターブ低い（DX Hard・CheezOrg が -2400 セント、SloRotar・GlaclRtr が
-1200 セント、RotaryOr が -100 セント）。ほかにも、鳴り始めに音程が動く音色（DuckLead・Bund など）が平らに鳴る。

MAME はスロット 0x0B と 0x10 を読み捨て、内部ポート 4 を 0 で返している。firmware の書き方を
時刻つきで追うと、これは声ごとのピッチ EG だった。

* スロット 0x10 は目標。下の 14bit が符号付きで、ピッチ（スロット 0x11）と同じ目盛り（1 オクターブ 1024）。
  音色の要素のノートシフト（DX Hard の -24 など）もここに入る。firmware は bit 15-14 を残して書き直す
  （`0x12E674`、`0x12E6D8`）
* スロット 0x0B の bit 14-8 は速さ。firmware は bit 15 と下の 8bit を残す
* キーオンの前に初めのレベルを書き（`0x12E004`）、キーオンの直後に最初の段の目標を書く（`0x12E710`）。
  そのあと内部ポート 4 の bit 14（着いた印）を読んで（`0x12E908`）次の段を書く（`0x12B81C`）
* 今の値は bit 14 に関係なくピッチに足す（下の追記）

直し方: 声ごとに目標・速さ・今の値・着いた印を持ち、毎サンプル今の値を目標へ近づける。刻みは音量の EG の
`level_step` を、速さから 16 引いて引く（4 分の 1 の速さ）。キーオンで今の値を目標にそろえる。

実機（MU2000EX、S/PDIF）との比べ:

| | 直す前 | 直した後 |
|---|---|---|
| 12 音色（DX Hard など）の音程の差 | -2400〜+10 セント | 全部 0 セント |
| DuckLead の鳴り始め（4ms おき、実機 -161 -117 -63 -2 +54 +86） | 平ら（+100） | -161 -117 -63 -2 +54 +86 |
| 100 のパフォーマンスの C4、1/3 オクターブ帯の食い違いの平均 | 1.37dB | 1.18dB |

速さを 16 引かずにそのまま使うと DuckLead の山が 4 倍早く、24 引くと 2 倍遅い。Bund（-75 セントから 0、60ms）
と VoxLead の揺れも同じ 16 で合う。

**追記（2026-09-16）— 16 より小さい速さ。** ここは長く「実機で確かめていない」まま 0 で止めていたが、
実機は表の下へそのまま続いていた。issue #3 で挙がった FF7 の XG 版の「woosh」がこれだった。

XG の SFX「Starship」（バンク MSB 64 の 88 番）は**速さ 8**、つまり表の底より 8 段下を使う。
表は 8 段下がるごとに半分の速さなので、0 で止めると**ちょうど 2 倍速い**。
ノートを 1 つだけ鳴らして 0.15 秒おきにスペクトルのずれを測ると

| | 実機 | 直す前 | 直した後 |
|---|---|---|---|
| 1.6 秒でのピッチの登り | +0.75 半音 | +1.55 半音 | +0.75 半音 |
| 実機との差（全区間） | — | 0 → +0.89 半音 | **全点 0.00 半音** |
| 1/3 オクターブ帯の差（この声だけ、平均/最大） | 0.18-1.04（実機どうし） | 2.89 / 10.10 dB | 1.21 / 4.24 dB |

`level_step` の引数を符号付きにするだけでよい。`k0 = level >> 3` が算術シフトで負まで伸び、
シフト量が増えてそのまま半分ずつ遅くなる。速さが 16 未満の声すべてに効く。

こちらのコミット: `swp30.cpp` の `peg_step`、`pitch_offset_w`、`internal_r` の 4、`streaming_block::step`

**追記（2026-09-14）**: 初めは bit 14 の立った声だけ足していた（全部足すとパフォーマンス 074・026 がずれたため）。
その後 16 の直し（遅れて鳴る層が消える）のあとで比べ直すと、bit 14 の無い値も実機では効いていた。
68/2 は 2 つの要素に 0x3E00 と 0x0200 を書き、bit 14 で分けるとエミュが実機より 600 セント低い（184.9Hz の倍音列、
実機は 261.4Hz）。全部足すと 0 セントになり、12 音色・ピッチ EG の 5 音色・Mondo（0x3C00）など 10 音色の音程は
変わらず、100 パフォーマンスの平均も 1.14dB のまま（026 は 2.4 → 1.9dB）。bit 14 が何の印かはまだ分からない。

## 14. ループ点を越えたあとのピッチの制限を、符号なしでかけている（直した）

**症状**: 元の鍵に近いピッチで鳴らす音（ピッチのレジスタが 0 付近）に強いビブラートを掛けると、揺れが片側だけになる。
Square Lead（0/81）の C5 でビブラートの深さ最大（パート 1 のビブラート深さ 0x7F、遅れ 0）にすると、実機は ±185 セントで
対称に揺れるのに、エミュは +177 セントと −20 セントの間を往復した。

ピッチ（スロット 0x11）は 14bit の符号付き（1 オクターブ 1024。0x3EEF = −0x111）。`streaming_block::step` のオクターブと
端数の計算（`((pitch >> 10) + 8) & 15` と `pitch & 0x3ff`）は、u32 のまま符号付きとして正しく働く。ところがループ点を
越えると（`m_finetune_active`）、`pitch & 0x80000000` なら 0、`pitch & 0x4000` なら 0x3FFF と、**符号なしの 0〜0x3FFF で**
範囲をかける。0x0005 に LFO の −180 を足すと 0 に張り付き、0x3F24 に +200 を足すと 0x3FFF に張り付く。

直し方: ピッチを 14bit の符号付きに広げてから LFO と微調整を足し、範囲は −0x2000〜0x1FFF でかける。ループ点の前と、
範囲に掛からないときの結果は今までと同じ。

こちらのコミット: `swp30.cpp` の `streaming_block::step`

## 15. LFO がキーオンで乱数から始まる。三角波の位相が 1/4 周期ずれている（直した）

**症状**: 同じ音を何度弾いても、ビブラートやトレモロの始まり方が毎回違う。2 層の音色で、1 回目だけ音量が大きく
落ちてから戻る（ChrchBel 96/15。issue #3 の「片方の層が早く止まる」）。

MAME はキーオンで LFO のカウンタを乱数にしている。実機（MU2000EX、S/PDIF）で同じ音を 4 回ずつ録ると、ビブラートは
4 回とも 3 セント以内で同じ形、ChrchBel のトレモロ（鋸歯状波、深さ 0x14）も 3 回とも同じだった。

* カウンタはキーオンで 0 にすると、鋸歯状波のトレモロ（ChrchBel）が実機と 3 回とも合う
* 三角波は MAME の式のままだとカウンタ 0 で一番下から始まるが、実機は中央から上がり始める。カウンタに 0x10000 を

* 矩形波とサンプル＆ホールドは実機で確かめていない（サンプル＆ホールドは乱数のまま）

乱数は MEG のディザと同じ数列から引いているので、エミュでは引く回数を変えずに捨てている。

100 パフォーマンス（C4）の帯の食い違いの平均は 1.18dB のまま、12 音色の音程差は全部 0 セントのまま。

## 16. release の速さが 0 でなければ release に入れている（直した）

**症状**: 2 層の音色で、少し遅れて鳴り始める層が立ち上がりの直後に消える（Synth Strings 0/51、Carillon 97/15、
ChrchBel 96/15 など。issue #3 の「片方の層が早く止まる」）。

firmware は層を少し遅らせて鳴らすとき、キーオンの直前に release_glo（スロット 0x09）へ 0x01xx を書く（pc 0x12E3DE）。
MAME の `release_glo_w` は上のバイトが 0 でなければ release に入れ、decay 2 の終わりでも上のバイトが 0 でなければ
release へ進む。0x01 は `^ 0x80` で 0x81 になり 1 サンプルに 0x7F ずつ落ちるので、その層は立ち上がりの直後に消える。
実機（MU2000EX、S/PDIF）では 0/51 の 2 層は同じ強さで鳴り続け、基音の山が 260.59Hz（−3dB）と 261.89Hz（0dB）に並ぶ。

「release せよ」の印とみて、release に入る条件を `& 0xff00` から `& 0x8000` にした。0/51 の 2 層がエミュでも
260.63Hz（−4dB）と 261.85Hz（0dB）に並ぶ。

100 パフォーマンス（C4）の帯の食い違いの平均が 1.18 → 1.14dB。層が欠けていた分、音量の差が普通の値（+12.9dB）に
近づいた（011 Superstrings +9.6 → +12.7、045 2 Octaves +8.7 → +11.6、090 Pad Swell +10.3 → +12.0）。

bit 15 が立っていない 0x01〜0x7F に、実機で意味があるか（遅い release など）は確かめていない。

## 18. 音が止んでも 0 に戻らない。MEG の丸めが 2 か所違う（直した）

**症状**: パフォーマンスモードで 1 音鳴らして離すと、実機は約 4 秒で S/PDIF がぴったり 0（-240dB、全サンプル 0）になる。
エミュはいつまでも -66dB の雑音と直流が残る（MAME も同じ）。

原因は 2 つで、**両方直さないと 0 にならない**:

* `meg_pack24` が p（27.15）を `>> 15` で負の無限大の側へ切り捨てていた。IIR の段（マスター EQ など）が音の止んだ
  あとも 1 LSB ずつの行き来を続ける。0 の側へ切り捨てる（`p / 32768`）
* `revram_decode` が e = 0 の負の値を 0xFFFFFFE0 で反転していて、下の 5bit が反転されない。-1 を詰めて戻すと
  -32 になり、リバーブの尾に小さな負の値が膨らんで残る。`revram_encode` のちょうど逆になるよう全部反転する

同じ曲（パフォーマンス 001、C4 を 1 秒、離して 10 秒）で、鍵を離してからの 1 秒ごとの音量（エミュは実機より
約 13dB 大きいのがいつもの差）:

| | +1s | +2s | +3s | +4s | +5s | +6s 以降 |
|---|---|---|---|---|---|---|
| 実機 | -48 | -64 | -83 | -103 | **-240** | -240 |
| 直す前 | -35 | -52 | -64 | -66 | -66 | -66〜-68 |
| 切り捨てだけ | -35 | -52 | -68 | -81 | -82 | -78 |
| 反転だけ | -35 | -52 | -64 | -69 | -70 | -70 |
| 両方 | -35 | -52 | -68 | -90 | -119 | **-240** |

両方直すと、実機より 1 秒遅れてぴったり 0 になる。100 パフォーマンス（C4）の帯の食い違いの平均が 1.137 → 1.111dB
（012 Old EP 1.00 → 0.00、049 1.70 → 1.00、099 1.30 → 0.80、047 だけ 0.60 → 1.30）。
make test の曲の直流も下がった（piano +6.3 → +2.1、effects +12.0 → +6.8、bend +6.7 → +1.6）。

こちらのコミット: `swp30.cpp` の `meg_pack24` と `meg_state::revram_decode`、`swp30_jit.cpp` の同じ所

## 19. 圧縮サンプルの展開の、差分の減り方と積算器の漏れが違う（直した）

**症状**: XG モードの圧縮サンプル（モード 0〜2）の音色で、エミュだけ直流が実効値の -0.07〜-0.34 ほど寄り、
30Hz 以下が多い（dense の試験曲の Trumpet で 20%、実機 0.5%）。MAME は差分を 0 へ丸めて 7/8・3/4・1/2 に減らし、
積算器を 3/128 ずつ漏らしている。

**決め方**: 実機でなく ROM のサンプルそのもので形を決めた。XG の 134 音色で音域全体を鳴らし、使われた
84 本の圧縮サンプルを、何百通りもの展開のしかた（漏れ、丸め、端数の桁、負の差分の作り方）で同時に展開して、
サンプルごとの直流/実効の中央値を比べた。元の楽器の録音に直流は無いので、正しい展開ほど 0 に近い。

差分を 8bit の端数つきで持ち、**k(差分 - 1)/d**（k/d = 7/8, 3/4, 1/2）で減らして、積算器へは下へ丸めて足すと、
3 つのモードが同じ式で揃う:

| 展開のしかた | モード 0 | モード 1 | モード 2 |
|---|---|---|---|
| 漏れ無し・0 へ丸め | 0.923 | 0.845 | 0.814 |
| 漏れ 3/128・0 へ丸め（MAME） | 0.223 | 0.146 | 0.061 |
| k(差分 - 1)/d、漏れ 1/128 | 0.010 | 0.008 | 0.007 |

端数を持たない整数のままでは、どう丸めても 3 つのモードが揃わない（漏れ無しで比べると、端数つきは 0.12〜0.19、
整数は 0.77 以上）。漏れの量は直流では決まらない（多いほど 0 に近い）ので、実機（XG モード、S/PDIF）の録音で決めた。
1/256 だと Trumpet の 30Hz 以下が 7%（実機 0.5%）、3/128 近くまで増やすと AltoSax の低い音などで 1〜8 倍音の並びの
食い違いが 0.15 → 0.29dB に離れる。1/128 にした。

実機との比べ（直流/実効、区切りごと）:

| | Trumpet 52 | Trumpet 56 | AltoSax 54 | AltoSax 58 | Tuba 54 |
|---|---|---|---|---|---|
| 実機 | +0.03 | +0.03 | -0.01 | -0.01 | -0.00 |
| 直す前 | -0.17 | -0.20 | -0.34 | -0.25 | -0.13 |
| 直した後 | +0.01 | +0.02 | -0.03 | -0.01 | -0.02 |

make test の dense（16 パート）は、帯の食い違い 0.58 → 0.51dB、直流/実効が実機 +0.024 に対して -0.014 → +0.031。

モード 3 の音は 1 ビットも変わらない。パフォーマンスモードの 100 パフォーマンス（C4）の帯の食い違いの平均は
1.111 → 1.101dB（002 Stereo Grand 4.4 → 3.5、悪くなったものは無し）。

残り: モード 0 の OldEP・OldPiano では、どの展開でも基音より下（18〜225Hz）に実機に無い成分が +20〜38dB 残る。
AltoSax の音 70 には 112Hz の余計な音が立つ。どちらもまだ分からない。

### 追記（2026-09-16）: 実機の出力そのもので形を決め直した

上の k(差分 - 1)/d・漏れ 1/128 は近似だった。実機の展開は次の形で、**積算器は漏れず、端数は捨てずに持ち越す**:

```
D     = 差分 + 展開表[入力]
積算器 = clamp(積算器 + D, -(0x8000 >> scale), 0x7fff >> scale)     出力は 積算器 << scale
Deff  = 実際に積算器に足せた量（切り詰めたときは D より小さい）
y     = k·Deff + r                    k/d = 7/8, 3/4, 1/2（モード 0, 1, 2）
差分  = floor(y / d)
r     = y mod d が 0 なら 0、そうでなければ (y mod d) - d     （-d < r <= 0）
モード 3 は 差分 = 0
```

**決め方**: galibert さんが MAME のコミット b75872cb の議論で公開した、実機から取り出した出力を使った。
同じピアノの圧縮サンプル 1 本（8 万サンプル）を、SWP00（MU50）ではモード 2・スケール 4 で、SWP20（MU80）では
形式の値 32 通りすべてで鳴らしたもの。SWP20 のモード 2・スケール 4 の形は TaleTN さんが先に見つけていた
（端数を frac と latch の 2 つの変数で持ち越す形で、上の r と同じもの）。

* SWP00: 上の積算器を 1 サンプルずらして `<< 4` すると、7 万サンプルがすべて一致する
* SWP20: スケール 1〜7 の 28 通り（4 モード × 7 スケール）が、各 8 万サンプルすべて一致する（値の刻みの中で）。
  上限に張り付くものも含む。上限に当たったときに「差分を 0 にする」（MAME）や「そのまま」（前のこちら）では、
  張り付いた直後から合わなくなる。**足せた量 Deff から次の差分を作る**と全部合う
* スケール 0 の 4 通りは、SWP20 の値の刻み（展開表に 511 倍の端数が乗る）のせいで比べられなかった

**実機（MU2000、S/PDIF）との比べ**。素のピッチ（ピッチレジスタ 0）で鳴らした圧縮サンプルの、倍音の線を除いた帯の強さ（dB、全体比）:

|---|---|---|---|---|
| モード 2（0/66/61）実機 | -74.7 | -81.4 | -82.4 | -69.2 |
| 前 | -47.7 | -48.6 | -51.7 | -54.5 |
| 直した後 | -76.4 | -82.1 | -85.3 | -69.4 |
| モード 1（0/65/1）実機 | -65.6 | -64.8 | -64.3 | -61.9 |
| 前 | -34.7 | -33.2 | -37.0 | -39.6 |
| 直した後 | -68.1 | -68.3 | -68.1 | -65.4 |

モード 2 は倍音の位相の食い違いも 0 になった（前は 1/f の形で残っていた）。倍音の間の雑音を展開の伝達で割った量は、

モード 3 は 1 ビットも変わらない。上の「残り」の AltoSax の音 70 の 116Hz の山も、前 -32.7dB → -57.2dB
（実機 -57.2dB）で消えた。

## 20. MEG の飽和する命令が、止める前に 42bit で折り返している（直した）

**症状**: 歪み系のエフェクトを強くかけると、実機には無い偶数倍音が出る（issue #8）。

MAME の `meg_state::step` は、掛け算・足し算・シフトのあとで p を 42bit（27.15）に折り返し（`util::sext(r, 42)`）、

## 21. 掛け算の無い形（mmode 0）の命令で、シフトと飽和を飛ばしている（直した）

**症状**: MU2000 のインサーション V DT HARD / SOFT（種類 0x62）がほとんど鳴らない（issue #8）。
弱く弾くと完全に無音、強く弾いても実機より 40〜50dB 小さい。

MAME の `meg_state::step` は、掛け算の形（bit 0x16-0x17、mmode）が 0 の命令では演算を丸ごと飛ばす。
V DT のプログラムには、mmode が 0 なのにシフト（<<4）と飽和（=s）のビットだけが立った命令がある:

    0d0  73812801  p =s (od * r25) << 4
    0d1  70000000  p =s p << 4           ← MAME では何もしない
    0d2  00020000_70000000  p =s p << 4 ; r02 = p   ← MAME では r02 = p だけ

Overdrive の係数（0d0 の定数、od 0 で 0x0008、100 で 0x7fff）のあとに 2 回 <<4 して飽和させ、
256 倍で歪ませる段になっている。飛ばすとゲインが 1/256 になり、そのあとの段では値が数 LSB になって丸めで消える。

直し方: mmode が 0 でも、シフトか飽和のビットが立っていれば、掛け算の項を 0 として同じ流れ
（足し算・シフト・飽和）を通す。手元のダンプでこの形が出るのは V DT だけ（20 か所）。

見つけ方: 実機の Overdrive 0 の音量がエミュの係数 0x0820（ほぼ 256 倍）と、実機の既定値（0x0083）がエミュの 0x7fff と
3 ベロシティとも 0.5dB 以内で合ったので、256 倍の置き場所を探した。

実機（XG モード、S/PDIF）との比べ。SineLead の A3 をインサーション 1 に通したときの音量（dB）:

| | 実機 | 直す前 | 直した後 |
|---|---|---|---|
| V DT HARD ベロシティ 30 / 70 / 127 | -42.9 / -29.4 / -28.0 | 無音 / -81.2 / -67.9 | -43.0 / -29.4 / -28.0 |
| V DT SOFT ベロシティ 30 / 70 / 127 | -51.0 / -37.1 / -27.4 | 無音 / -111.0 / -77.8 | -51.1 / -37.1 / -27.4 |

飽和している組（HARD の 70・127、Overdrive 36 と 100、SOFT の 127）は、2〜6 倍音のレベルも実機と dB 単位で一致した。
issue #8 の曲の ch2（V DT HARD）は 1/3 オクターブ帯で実機と ±1.6dB 以内、曲の冒頭 30 秒の帯の食い違いは 1.47 → 0.25dB。

## 24. bit 0x23 の付いたメモリ読み出しは、リバーブ RAM の絶対番地を読む。直に書く値は 8 倍大きい（直した）

**症状**: XG のエフェクトの RING MOD・SLICE・AMP SIM 2・MULTI COMP・LOW RESO・AUTO PAN 2・D.TURNTBL・D.SCRATCH が
鳴らないか、実機と音がまるで違う。

これらのプログラムには、MAME が解いていない bit 0x23（MAME の表の「--II--J-」の左の「-」）の付いたメモリ読み出しがある
（例: RING MOD `0000002a00810800  mem_r +80+idx`）。MAME はふつうの読み出しと同じく
`offset + idx - サンプルの数え上げ` を map で区画に割り当てて読むので、何も書かれていない場所を読んで 0 になる。

firmware は、これらの種類を読み込むときに、**波形や曲線の表をリバーブ RAM の 0 番地付近へ直に書いている**
（0x94e/0x94f に番地、0x98e/0x98f に値）。RING MOD は 0x000 から 257 語（256 点で 1 周の正弦と補間用の 1 点）、
AUTO PAN 2 は 0x000・0x404・0x808・0xc0c から 1025 語ずつ（0〜1 の三角波が 2 つ、0〜1 に持ち上げた正弦が 2 つ）。
bit 0x23 の読み出しは、この表を **`offset + idx`（+1）の絶対番地** で引く。サンプルの数え上げを引かず、map も通さない。

直に書く値は上の 16bit が Q15（1.0 = 0x7fff、下の 16bit は 0）。MAME の `revram_data_w` は `>> 5` してから詰めるが、
MEG がメモリへ書く値（`p >> 15`）の目盛りでは 1.0 が 2^23 なので、**符号付きで `>> 8`** しないと 8 倍（+18dB）大きく入る
（`revram_data_r` も同じだけ戻す）。

実機（XG モード、S/PDIF）との比べ（インサーション 1 に SineLead の A3、強と弱。1/3 オクターブの帯の食い違いの平均）:

|---|---|---|---|
| AUTO PAN 2 | 12.4 | 15.1 | 0.1 |
| AMP SIM 2 | 無音に近い | 22.4 | 0.0 |
| RING MOD（256 点の正弦を決め打ちしていた） | 0.0 | 33.9 | 0.0 |
| LOW RESO | 無音 | 18.1 | 0.3 |
| D.SCRATCH | 61.6 | 26.3 | 0.8 |
| MULTI COMP | 無音 | 45.6 | 強 9.0（+9dB）/ 弱 3.0 |

AUTO PAN 2 は、LFO を遅くして左右のゲインを時間に沿って録ると、三角波の坂の傾きと持ち上げた正弦の形が実機と重なる。
bit 0x22（ロータリーの系統と V-FLANGER、MULTI COMP・V-FLANGER では 0x23 と一緒）の意味はまだ分からない。

**症状**: MU2000 の SAMPLING → REC で録音が始まらない。SAMPLING → SAVE でカードへ書き出すと「SAVING」のまま止まる。

MAME の `swp30_device` の波形アクセス（0x10e）は、1 語読む 0x8000 と続けて書く 0x5000 だけを持つ。MU2000 の firmware はほかに 2 つ使う。

* **0x7000 録音**: 番地（0x10c/0x10d。サンプリング RAM の先頭 0x1000000）と長さ（0x08e/0x08f、語数）を書いてから 0x7000 を書く。
  あとは 0x30f（書いた 16bit サンプル数の下 16bit）と 0x10f の bit 14（書き終わり）を読み続け、止めるときアクセスを 0 に戻す。
  1 サンプルごとに A/D 入力を 16bit で書き、32bit の語 1 つに 2 サンプル（下の 16bit が先）。
* **0x9000 続けて読む**（カードへの書き出し）: 番地と長さ（16 サンプルずつなので 8 語）を書いてから 0x9000 を書く。
  1 語ごとに、0x10f の下 8bit が 0 でなくなるのを待ち、`(0x10f & 0x40ff) == 0x4000` なら打ち切り、そうでなければ
  0x14e（上 16bit）、0x14f（下 16bit）の順に読む（firmware 2.01 の 0x1366c4）。
  エミュでは 0x9000 を書いたときに最初の語を用意し、残りがある間 0x10f は 0x0001 を返し、0x14f を読んだら次の語へ進める。

録るものは**ミキサの出力 8 の左**にした。MU2000 はスレーブの MELI 6（AD1）と 7（AD2）だけを出力 8 へ繋いでおき、REC の InputSrc
（AD1 / AD2 / AD1+2）でその 2 本の音量（`vol[0]` と `vol[1]`）を 0x00ff か 0xffff に書き換える。録音の先がミキサの出力だとすると、
firmware の書き込みだけで入力の切り替えが説明できる（実機の内部で出力 8 を録っている確証は無い）。

これで、録音 → SAVE（ALL+SEQ）→ 別の機械に差して LOAD で、サンプリング RAM が 1 バイトも違わずに戻る（`build/samptest.exe`）。
実機で 0x10f がどんな値を返すか（下 8bit が溜まった語数なのか）は分からない。firmware は 0 か 0x4000 かしか見ない。

こちらのコミット: `swp30.cpp` の `wave_access_w` / `wave_busy_r` / `wave_val_r` / `sample_step`

## 28. SH7042 の中速の A/D で、連続変換（SCAN）ができない（直した）

**症状**: MU2000 の SAMPLING → REC の画面で、レベルメーターが動かない。TriggerLvl を上げても「Waiting!」にならず、すぐ録音が始まる。

`sh_adc_device::mode_update()` の中速（`m_is_hs` が偽）の側に 2 つ問題がある。

* ADCSR の **bit 4 が SCAN、bit 3 が CKS**（H8 の `h8_adc_3337_device` と同じ並び）なのに、bit 3 を SCAN として見ている。
* `m_start_mode` を作らず `m_mode` に直接入れているので、`start_conversion()` が `m_mode = m_start_mode`（0）で上書きし、
  1 回変換して止まる。SCAN でも回り続けない。

MU2000 の firmware は起動してから ADCSR0 に 0xb3（ADF・ADST・SCAN、AN0-AN3）、ADCSR1 に 0xb0（AN4）を書いて回し続け、
REC の画面では ADDR0 / ADDR2 の上 8bit（A/D INPUT の大きさ）を直に読む（2.01 の 0x116196）。

直し方: 中速の側で、SCAN が 1 なら `m_start_mode = ACTIVE | REPEAT | ROTATE`、AN0 から CH まで。0 なら `ACTIVE` で CH だけ。
`timeout()` の REPEAT で ADST が下ろされていたら止める。

ついでに S-MU2000 では、割り込み（ADIE）を使わない連続変換は変換ごとに時計を刻まず、ADDR を読まれたときに入力を読むようにした
（`free_running()`）。1 変換ごとに刻むと、変換時間が 24 サイクルなので CPU の実行が 1 サンプルあたり 744 → 1607ns に重くなった。
こちらは MAME に持っていく必要はない（MAME は変換時間の見直しのほうがよい。SH7040 の中速は 1 変換 266 ステートほど）。

この直しで CPU の動くタイミングがわずかに変わり、make test の鳴らし比べの WAV が 1 LSB だけ違うところが出た（指紋を焼き直した）。

こちらのコミット: `sh_adc.cpp` の `mode_update` / `timeout` / `start_conversion` / `addr_r` / `adcsr_r` / `adcsr_w`

## 29. 乗算器の第 1 入力の選び方 2 は、直前の印で t と定数を切り替える（入れた）

**症状**: XG のエフェクトの MULTI COMP（0x69）が、閾値を越える音をまったく圧縮しない。実機（XG モード）は 9dB ほど下げる。

MAME の表の「P = mul 1st input = 0,3=constant, 1,2=temp register (note that 2 and 3 seem never used)」の P=2 は、
MU2000 の 116 種類の中で MULTI COMP だけが使う。3 つの帯の包絡線を追う所で、

```
0e4  p = 0.0625 * m01 - p ; m01 = p ; flags     入力の大きさ - 包絡線、印を立てる
0e5  p =_ r06 - m02 ; t1 = 0.000976562
0e6  p =s m02 + p ; m02 = p ; t2 = 0
0e7  p = t1 * r2b + r2b                          ← P=2（定数は -1.0）
0e8  p =s (t2 << 8) + p ; r2b = p                ← P=2（定数は 0.5）
0e9  p = 0.0242004 * r2b                         → 包絡線の係数
```

MAME のように P=2 を常に t とすると、r2b は 0 から動かず、包絡線が育たないので圧縮が掛からない。
**直前に印を立てた結果が負なら t、そうでなければ定数** とすると、入力が包絡線より上のときは r2b = 0.5 に戻し、
下のときは 1/1024 ずつ育てる形になり、実機と合う。逆の向き（負でなければ t）では圧縮が掛からない。

実機との音量の差（SineLead A3、CC11 で 6 段。どの段でもほぼ同じ差）:

| 設定 | P=2 を常に t | 印で切り替え |
|---|---|---|
| 既定 | +9.0dB | -1.2dB |
| パラメータ 3 = 0 | +16.8dB | +0.6dB |
| パラメータ 2 = 127 | +5.6dB | +0.8dB |
| パラメータ 3 = 127（圧縮しない） | 0.0dB | 0.0dB |

残りの ±1dB の出どころはまだ分からない（負だけでなく 0 も含める形では変わらない）。

こちらのコミット: `swp30.cpp` の `meg_state::step` / `run_program`、`swp30_jit.cpp` の同じ所

## 30. 掛け算の無い形（mmode 0）でも、加算器（p = 0 - p）はかかる（直した）

**症状**: XG のエフェクトの SLICE が、8 回刻むうち 4 回だけ 2 倍（+6dB）の大きさで鳴る。DYNA FLANG が実機より 5.6dB 大きい。

upstream 21 で、mmode 0 の命令にもシフトと飽和がかかることは入れた。けれども加算器（引き算）は飛ばしたままだった。

```
0de  p = m07                 m07 は刻みの形（0 か 1）
```

## 31. 分岐の命令も t レジスタに書く（直した）

**症状**: XG のエフェクトの DYNA PHASE が実機より 5.8dB 大きい。DYNA RING は音色がまるで違い、DYNA FLANG の弱い音は共鳴が動かない。

upstream 11 で入れた分岐（bit 0x3f）の命令を、エミュはメモリや m/r への書き込みの無い「何もしない命令」として扱っていた。
けれども DYNA 系の分岐の命令は、上の 8bit で **t レジスタへの書き込み** も指定している。DYNA PHASE の包絡線を追う所:

```
0df  0100000144940410  p =s t1 * m01 - p ; flags     (大きさ - 包絡線) / 16
0e0  0000c90002815921  p = 0 * r2b + m12 ; m12 = p
0e1  9a0000000ae91800  skip to 0e9 if !n || z ; t2 = p   ← 0x9a = 分岐 + t2 を p から書く
 ...
0eb  0200000003900800  p = t2 * r01                  包絡線に足す量 = (大きさ - 包絡線)/16 × 係数
0ec  0034000040c1a400  p =s r34 + p ; r34 = p
```

t を書かないと、0eb の t2 は前のサンプルでオールパスの係数を入れた値のままになり、包絡線がおかしな値になる。
フェイザーは素通りの音とオールパスを通した音を足すので、係数が違うと A3 での足し合わせが強め合って 6dB 大きくなっていた。
**分岐の命令でも、ふつうの命令と同じく t を書く**（p からなら 2 命令前の値、そうでなければ定数）。

実機（XG モード）との比べ（SineLead A3。1/3 オクターブの帯の食い違いの平均）:

| | 直す前 | 直した後 |
|---|---|---|
| DYNA PHASE | 強 +5.8dB / 弱 帯 26.2 | 強 0.0dB（包絡線も 0.1dB 以内）/ 弱 帯 4.6 |
| DYNA RING | 強 帯 39.4 | 強 帯 1.0 |
| DYNA FLANG | 弱 -17.1dB | 弱 -0.6dB（共鳴が動く形も実機と重なる） |
| DYNA FLT | 弱 帯 9.6 | 弱 帯 7.0 |

## 32. idx と mw の両方が立った命令は 2 つ目の idx に書き、bit 0x22 の読み出しがそれを足す（直した）

**症状**: XG のエフェクトの DT/OD/AMP +RTRY、DT/OD/AMP +2RTRY、DUAL ROTR1/2、V-FLANGER が、音量は合うのに、
倍音の間や低い帯域に実機より 30〜60dB 大きい濁りが出る。

これらのプログラムは、bit 0x3e（idx = p）と bit 0x3d（mw = p）の両方が立った命令を置き、その 3 命令後に、
bit 0x21（+idx）の無い、**bit 0x22 の付いた読み出し**を置く。DUAL ROTR1 の例:

```
0cf  400000344381d002  p =s 0.0245972 * r3a ; idx = p ; mem_1r +2
0d0  60005a804381d802  p =s 0.0245972 * r3b ; mw = p ; idx = p      ← bit 0x3e と 0x3d
0d2  1d3b002200840140  p = 0.03125 * m14 + p ; mem_r +2+idx          ← 0cf の idx
0d5  0000003200819801  mem_1r +2+idx
0d8  002f00244081b801  p =s 0.53421 * r37 + p ; mem_r +2               ← bit 0x22。0d0 の値を足す
0db  1a02003444940040  mem_1r +2                                       ← bit 0x22
```

ロータリーは 2 本の遅延線（ホーンとローター）を別々の揺れで読むので、idx が 2 つ要る。
**bit 0x3e と 0x3d が両方立った命令は、idx でも mw でもなく 2 つ目の idx に（3 命令遅れで）書き、
bit 0x22 の付いた読み出しは番地に 2 つ目の idx を足す**（bit 0x23 の絶対番地の読み出しでも同じ。V-FLANGER と MULTI COMP が使う）。
upstream 26 で「この命令は mw を取り込まない」としたのは半分だけ正しかった（idx にも書かない）。

実機（XG モード）との比べ（SineLead A3、強い音。帯は上位 40dB の中の食い違いの平均）:

| | 直す前 | 直した後 |
|---|---|---|
| DT +RTRY / OD +RTRY / AMP+RTRY | 16.6 / 12.2 / 2.7 | 0.1 / 0.1 / 0.1 |
| DT +2RTRY / OD +2RTRY / AMP+2RTRY | 37.0 / 34.5 / 28.5 | 0.1 / 0.1 / 0.0 |
| DUAL ROTR1 / DUAL ROTR2 | 36.3 / 36.4 | 0.1 / 0.0 |
| V-FLANGER | 43.4（-2.4dB） | 0.1（0.0dB） |
| MULTI COMP | -1.3dB | -0.8dB |

S-MU2000 では 2 つ目の idx の値と遅延の輪を meg_state の外（swp30_device）に置き、状態の保存の版を 6 にした
（MEG の印 flag_n/flag_z もこれまで保存していなかったので一緒に入れた）。

## 33. MAME の MEG の DRC が、インタプリタと 3 か所食い違う（MAME だけ。こちらは DRC を使っていない）

**症状**: MAME で同じ MIDI を `-nodrc` の有り無しで鳴らすと、HALL 1 からして差が信号と同じ大きさになる。

MAME に上の直しを移すときに、DRC とインタプリタを同じ状態から 1 サンプルずつ走らせて比べて見つけた:

* メモリアクセスの番地で、区画の先頭（map の下 8 ビット × 1024）を足してから区画の長さでマスクしていて、
  先頭が 0 でない区画が RAM の頭へ畳まれる。HALL 1 は 0x30000 の区画を使うので、遅延線が別の場所に入る。
  `resolve_address` と同じく、マスクしてから先頭を足す
* idx の値を、32bit の配列へ 16bit の `STORE`（2 倍の目盛り）で書いていて、遅延の輪の 0 番以外が壊れ、
  値も 16bit に切れる。32bit で書く
* `r = r` のコピーを 64bit の `DMOV` で 32bit の場所へ書いていて、隣の、まだ入っていない書き込みを潰す

直した後は `-nodrc` の有り無しで、ディザの 1 LSB ほどの差しか残らない。

MAME に投稿した PR（2026-09-15）: 22 は [mamedev/mame#16140](https://github.com/mamedev/mame/pull/16140)、
33 は [mamedev/mame#16141](https://github.com/mamedev/mame/pull/16141)。どちらも同じ日のうちに取り込まれた。
続けて 24 を [mamedev/mame#16142](https://github.com/mamedev/mame/pull/16142) に出した（#16140 で「リバーブ RAM に表を書いてどう使うのか」と
聞かれたので、その答えも兼ねる）。

MAME の PR 用ブランチ（tarboh/mame に push 済み。33 より後は前が取り込まれてから投稿）: `swp30-meg-drc-fixes`（33）、`swp30-meg-absolute-reads`（24）、
`swp30-meg-alu`（18・20・21・23・30）、`swp30-meg-branches`（11・29・31）、`swp30-meg-index2`（32）、`swp30-meg-lfo-phase`（25）。
2026-09-16: #16142 が取り込まれたので、`swp30-meg-alu` を MAME の最新に載せ直して [mamedev/mame#16151](https://github.com/mamedev/mame/pull/16151) に出した。残りの 3 本は、これが取り込まれてから載せ直す。

MAME に投稿した PR（2026-09-15）: [mamedev/mame#16144](https://github.com/mamedev/mame/pull/16144)。MAME（ほかの直しの入っていない状態）でも GM 128 音色の帯の食い違いの平均が 0.733 → 0.647dB になり、悪くなった音色は 0.05dB 以内。

## 35. 逆向きに鳴らすサンプルの補間で、4 つの値の並びが逆のまま（直した）

**症状**: XG の Electro Kit・Analog Kit の 28 番（8bit のサンプルを逆向きに、約 0.41 倍の速さで鳴らす）で、
エミュだけ 10〜20kHz が実機より +14〜25dB 多く、5〜6.4kHz が 7〜10dB 足りない。

`read_16` / `read_12` / `read_8` は、逆向き（loop の bit 31）のとき `spos = -m_pos` から番地の順に 4 つ読む。
再生の順では、読んだ val0 が「次」、val1 が「今」、val2 が「前」、val3 が「その前」になる。`step()` は順向きと同じく
val2 を「次」として端数で寄せるので、端数が増えるほど 1 つ前の値へ近づき、1 サンプルごとに行きつ戻りつする。
ぎざぎざの雑音が高い帯に出て、本来の高めの成分は削られる。

声の中身をダンプし（読んだ 4 つの値・端数・位置）、同じ補間の式で並びだけを再生の順に直して机上で計算すると、
実機の録音と 640Hz から上の帯で平均 0.20dB の差で重なる（直線補間 1.48、Catmull-Rom 1.92、窓付き sinc 8 タップ 5.93dB）。
フィルタの係数を変える案（この音はカットオフが最大・Q=1 で、Chamberlin がそのまま素通しになる）はどれも合わなかった。

直し方: 逆向きのときは 1 つ手前（`-m_pos - 1`）から読み、`step()` で val0↔val3、val1↔val2 を入れ替える。
これで前・今・次・その次の順になり、「今」の値は直す前と同じ。圧縮サンプル（`read_8c`）は逆向きが無いので触らない。

XG のドラムキット 10 種 465 音で、帯の食い違いの平均が 0.272 → 0.252dB。Electro・Analog の 28 番は 3.9 → 0.1dB 前後に下がり、
スタンダードキット 71 音と GM 128 音色は数字が 1 つも変わらない。make test も変わらない。

こちらのコミット: `swp30.cpp` の `read_16` / `read_12` / `read_8` と `streaming_block::step`

MAME に投稿した PR（2026-09-15）: [mamedev/mame#16143](https://github.com/mamedev/mame/pull/16143)。MAME でも同じ音の帯の食い違いが 5.67 → 0.17dB になった。

## 36. SWP30 への書き込みで CPU が待たされない（直した）

**症状**: 2 層の音色で、遅れて鳴る層（firmware が 2.5ms ごとに 5 ずつ減らす数が 0 になったら鍵を押す層。
French Horn・Music Box・Syn Strings・Slap Bass 2 など）の遅れが、実機より平均 63〜65 サンプル（約 1.45ms）長い。
遅れの長さに比例せず、ばらつきの幅（2.5ms）は実機と同じ。層どうしのうなりや、同じ高さの基音の打ち消し合いの形が変わる。

遅れの数は、鍵を押す少し前（音の設定を書く前）に置かれ、最初の層の鍵を押すまでの間に、firmware は
その音のレジスタを 100 回ほど書く。エミュではこれが 0.2ms で終わるが、実機では約 1.7ms かかっていると考えると
遅れの範囲がそのまま合う。1 命令を 4 サイクルにして CPU を一律に遅くしても平均は 770 サンプルまでしか寄らず、
それ以上遅くすると別の所が崩れる。「SWP30 のレジスタを書くと、CPU は次のサンプルの区切りまで待たされる」
（書き込みを 1 サンプルに 1 回しか受け取れない）とすると、平均も幅も合う:

| French Horn C4、24 回 | 平均 | 最小 | 最大 |
|---|---|---|---|
| 実機 | 752.5 | 703 | 804 |
| 待たせない（直す前） | 815.5 | 761 | 865 |
| 書き込みごとに次のサンプルの区切りまで待たせる | 749 | 688 | 807 |

Music Box を 8 回、同じ MIDI で鳴らすと、音ごとの遅れが実機と ±16 サンプル以内で並ぶ（1 回だけ、2.5ms の刻みの境目で 1 刻みずれた）。
待たせる書き込みを声のレジスタだけに絞ると 10〜20 サンプル長くなるので、ミキサや IIR の書き込みも待つ。
制御の 2 つ（0x0e / 0x0f：鍵を押す合図と覆い、MEG のプログラムの番地と中身、波形とリバーブ RAM の直の読み書き）は
待たせない（待たせると MEG のプログラムの読み込みが何秒にも延びる）。

**待つのはマスタの SWP30 だけ（同じ夜に絞った）**: スレーブにも待たせると、2.4kHz の割り込みが毎回スレーブのミキサを 7 つ書くので
CPU の 4 割が止まる。スレーブを待たせない形にすると、Music Box の 8 回が全部 ±9 サンプル以内（全部待たせる形では 1 回だけ 2.5ms の刻みで外れた）、
French Horn の 24 回が平均 751.4・最小 696・最大 800（実機 752.5・703・804）と一段よく合い、SLICE の位相も 51 → 40ms に戻る。
ミキサの書き込み（0x32 から上）を待たせない形は、遅れが実機より 10 サンプルほど長くなるので違う。

直し方: `mu2000.cpp` のバスで、マスタの SWP30 の 0x0e / 0x0f 以外を書いたら `abort_timeslice()` で CPU を止め、
そのサンプルの残りは命令を進めずに時間（`skip_cycles`）だけ進める。タイマや MIDI の送出は区切りごとに進む。

GM 128 音色（C4・C6・C2）とドラムキット 10 種の帯の食い違いの平均は、0.169→0.171、0.366→0.372、0.173→0.145、
0.118→0.118、0.252→0.249dB で、目立って悪くなった所は無い。試験の曲の指紋は焼き直した。
SLICE の刻みの位相（効果を選ぶ SysEx から数えて実機 9ms）は 34 → 51ms（マスタだけにした後は 40ms）と遠ざかった（効果を替えるときのミキサの
書き込みが待つため。SLICE の元のずれの原因は別にあり、まだ分からない）。

**制御の 2 つのうち、中身を書くものも待つ（同じ深夜に足した）**: エフェクトの種類を SysEx で替えると、音が途切れてから戻るまでが
実機は DISTORTION・OVERDRIVE・THRU で 175〜195ms、SLICE で 240〜243ms、エミュは 165〜184ms と 178〜180ms だった（音を伸ばしたまま
切り替えて 1ms で測った）。SLICE は読み込み中にリバーブ RAM へ表を 2052 項目書く。MEG のプログラムの中身（チャンネル 0x11・0x12 の
0x0e/0x0f）とリバーブ RAM へ直に書く中身（0x26）の書き込みでも待たせ、番地（0x10・0x25）・合図・状態の読み書きは待たせない形にすると:

| | ほかの種類の戻りの差 | SLICE の戻りの差 | SLICE の刻みの位相の差 |
|---|---|---|---|
| 待たせない | 平均 -13.5ms | -62ms | +50〜56ms |
| 中身の書き込みで待つ | 平均 -1.2ms（絶対値 4.1） | +16ms | +4〜9ms |

プログラムの中身を 1 組ずつ・RAM の番地も待つ、など 15 通りを試した中で、この形が一番合い、決まりとしても筋が通る。
SLICE の位相の試験（選んでから弾くまでを 0〜1 秒ずらした 9 回）でも、エミュ 12〜14ms・実機 3〜15ms（前は 34〜40ms）。
遅れて鳴る層の遅れは変わらない（音の設定の書き込みはこの 3 つを使わない）。エミュの読み込みの終わりが 20ms 刻みで揺れるのは、firmware の 50Hz の処理の刻みによる。

MAME も CPU と SWP30 の書き込みを同じように扱っていて、同じ差があるはず（MAME では `sh7042` 側でバスの待ちを入れることになる）。

**追記（2026-09-16）: 鍵の時刻の精度を測り直した**。これまでは「遅れて鳴る層」の遅れで測っていたが、
音色の違いのせいで相関が効かず、±16 サンプルまでしか言えなかった。**2 つのパートを左右に振り分けて、
同じ時刻に 2 つのノートオンを送る**形にすると、片方ずつ立ち上がりを測れる（scratchpad の twonote.py・twonote.mid）。
音色は立ち上がりの鋭い木琴。MIDI の時刻を 0.217ms ずつずらした 24 回で、実機（XG モード、S/PDIF）と比べた。

* 鍵の時刻は、実機もエミュも**約 44 サンプル（1ms）の刻みに量子化**されている。刻みが飛ぶ位置（24 回のうち 5 か所）も一致する。
* 実機の録音は、PC の MIDI の時計と MU2000 の水晶の差で **14ppm** ずつ流れる（1 次式で取り除いた）。
* それを除いた鍵の時刻の差は、**幅 11.4 サンプル・標準偏差 3.6 サンプル（81 マイクロ秒）**。立ち上がりの波形どうしの
  相互相関（4 倍に補間）で測っても同じ数字なので、測定の誤差ではなく本当の差。
* 残っている差は 1ms の刻みの中での位相に連動している（同じ刻みの中では ±4 サンプルほど系統的にずれる）。

**まだ合っていないもの**: 続けて送った 2 つのノートオンの間隔が、実機はばらつくのに、こちらはほぼ 42 サンプル
（MIDI の 3 バイト = 30 ビット時間ちょうど）で固定になる。

| 送り方 | 平均 | 幅 |
|---|---|---|
| 実機 USB（HOST SELECT が USB） | 39.6 | 37〜42 |
| 実機 DIN（HOST SELECT を MIDI にして、MIDI IN A へ） | 38.6 | 36〜44 |
| こちら | 42.0 | 41〜43 |

**経路の違いではない**（USB でも DIN でも実機は 3〜4 サンプル短い）。エミュの中を見ると、2 つ目のメッセージの
最後のバイトは 1 つ目のちょうど 26890 サイクル後（= 30 ビット時間）に届き、鍵もその通り 42〜43 サンプル後に押される。
実機は 2 つ目の鍵がそれより 3〜4 サンプル早いので、firmware が続けて届いたメッセージを 1 つ目より速く処理している
（2350 サイクルぶん）ことになる。CPU をわざと遅くしても実機に近づかない（1 サンプルあたり 20・60 サイクル飛ばすと
42.2・43.2 と逆に伸びる）ので、CPU 全体の速さの話でもない。割り込みの待ち時間か、firmware の主ループの回り方らしい。
残る差は 77 マイクロ秒ほど。

**追記（2026-09-16 深夜）: 1 パートぶんの設定にかかる時間を、実機で ±1 サンプルで測った**。
XG モードで、**パート 1 と 2 を同じ受信チャンネルにして 1 つのノートオンで鳴らし、左右へ振る**
（音色はどちらも SineLead、リバーブ・コーラス・バリエーションの送りは 0、ほかのパートは受信を切る。
scratchpad の xglayer.py・tlgap.py）。1 つのノートオンで 2 パートが順に立ち上がるので、
左右の立ち上がりの差がそのまま「firmware が 1 パートぶんのレジスタを書く時間」になる。
これは**層どうしの時刻差と同じ量**で、しかも波形から直に読める。

| | 平均 | 最小 | 最大 | 標準偏差 |
|---|---|---|---|---|
| 実機（8 音） | **61.4** | 61 | 64 | 1.0 |
| こちら（8 音） | **79.0** | 79 | 79 | 0.0 |

**こちらが 17.6 サンプル遅い**。2 つのキーオンの間に firmware が書くレジスタは 89 本で、
うち 20 本は制御（0x0e/0x0f、待たせない）なので、**待つ書き込みは 69 本**。こちらはそれを
69 サンプル（1 本 1 サンプル）＋ CPU の仕事 10 サンプルで 79。実機は同じものを 61 で終える
（69 本を 51 サンプル ＝ 1 サンプルあたり約 1.35 本）。

**試した形は 3 つとも当たらなかった。**

| 形 | 2 パートの差 | French Horn の包絡 | 100 パフォーマンス |
|---|---|---|---|
| いまの形（書くたびに待つ） | 79 | **0.133** | 0.584 |
| 1 サンプルに 1.375 本受け取る | **61.1** | 0.200 | **0.565** |
| 受け皿（深さ 14〜20） | 68（深さを変えても動かない） | 0.24〜0.31 | — |
| IIR（0x20-0x2b）とミキサ（0x30-0x3f）は待たせない | 55（24 本ぶん引ける） | — | — |

比例して速くする形は 2 パートの差と 100 パフォーマンスの物差しを良くするが、
**遅れて鳴る層（French Horn の 24 音、包絡の形で比べた。scratchpad の hornenv.py）を悪くする**。
受け皿の形は、キーオンの間の書き込みが一続きではないので深さを変えても効かない。
待たせない並びを作る形は行き過ぎる。どれも実機の 61 と 0.133 を同時には満たさない。

コードは変えていない。**61.4 ± 1.0 サンプルという数字が、次の形を決めるときの的**になる。

**その続き（同じ夜）: 速くする形は「鍵の絶対時刻」も動かしてしまう**。1 サンプルに
1.375 本受け取る形にすると、2 パートの差は 79 → 62 と的に当たるが、**1 つ目のキーオンも
16 サンプル早くなる**（521372 → 521356）。この追記の上で詰めた「鍵の時刻は実機と
標準偏差 3.6 サンプルで合う」は、そのぶん崩れることになる。

つまり探している形は、

* キーオンとキーオンの間（この試験では待つ書き込み 69 本）を **18 サンプル縮める**
* 1 つ目のキーオンの時刻は **動かさない**

の両方を満たすものでなければならない。1 つ目の鍵の時刻は 1ms の刻みに量子化されている
ので、「実機では鍵を押す前の書き込みが刻みより前に終わっていて、こちらでは終わっていない」
という形なら両方を説明できる。それを確かめるには、ノートオンの時刻を 0.2ms ずつずらして
階段の段の位置を実機と比べる試験（scratchpad の xgstair.py・stairan2.py）が要る。
こちらは段がきれいに出る（24 音のうち 1 か所で 61 サンプル飛ぶ）が、実機の録音は
音の対応付けが途中で飛ぶ。調べると**録音の取りこぼしではなく、MIDI の送出そのものが
ときどき数十 ms ずれている**（rec.exe。24 音のうち 1 音が 88.6ms 早く届いていた）。
送り手の時計を当てにする測り方は、この粒度では使えない。

**送り手の時計に頼らない形を作った**（scratchpad の xgfill2.py・fillan.py）。
同じ刻みに `[ノートオン ch2] [詰め物] [ノートオン ch1]` を並べる。塊の中では
**伝送そのものが時計**になるので、2 つ目のノートオンは 1 つ目のちょうど（バイト数）ぶん
後に届き、送出が数十 ms ぶれても 2 つの差は変わらない。詰め物は正しい MIDI メッセージで
なければ SMF が壊れるので、受け持ちを外したチャンネル 16 へ 2 バイト（チャンネル
プレッシャー）と 3 バイト（ノートオフ）を混ぜて入れる（640 と 960 マイクロ秒の
組み合わせで 320 マイクロ秒刻みが作れる）。

これで分かったこと:

* **実機の録音は USB 経由**（HOST SELECT が USB）。詰め物 12 バイトで左右の差が
  23 サンプル伸びる ＝ 1 バイト約 1.9 サンプルで、USB の速さ。DIN の 31250bps なら
  1 バイト 14.11 サンプルなので、**エミュ側も `--usb` で流さないと比べられない**。
  こちらを DIN で流すと 12 バイトで 145 サンプル伸びてしまう。
* **2 パートの差（79 対 61.4）は口の違いではない**。`--usb` で流し直しても
  こちらは 79.0 のままで、実機の 61.4 との 17.6 サンプルは残る。
  1 つのノートオンが全部届いたあとの話なので、当然ではある。
* こちらは USB で流すと、詰め物に対する応答が**二山に割れる**（左右どちらのパートが
  先に立ち上がるかが音ごとに入れ替わり、差が約 19 と約 83 に分かれる）。実機は
  66〜90 の一山。USB ではバイトがほぼ同時に届くので、順番が入れ替わりやすい。
  ここはまだ詰められていない。

**結び（2026-09-17 未明）: 書き込み 1 本を 440 サイクルにしたら、全部の物差しが合った**。

まず、左右の出力そのものに時刻差が無いことを確かめた（1 パートをセンターで鳴らして
左右を突き合わせると実機 −0.000 サンプル・こちら −0.002。振り分けを 32〜96 に変えても
どちらも ±0.013 サンプル以内で、振り分けの利き方も右/左の比が 0.385/0.649/1.000/1.540/2.597 対
0.386/0.650/1.000/1.539/2.590 と 0.3% 以内で合う）。**測った 17.6 サンプルは本物**。

次に、キーオンとキーオンの間の書き込みを、チップを分けて数え直した（`--trace-swp`）。
**マスタで待つ書き込みは 68 本**、スレーブは 5 本。こちらはそれを 68 サンプル
（1 本 1 サンプル）＋ CPU 11 サンプルで 79。実機の 61.4 に収めるには、1 本あたり
**0.69 サンプル ＝ 440 サイクル（15.7 マイクロ秒）**でなければならない。

「1 サンプルの区切りまで待つ」形をやめ、**1 本あたり 440 サイクルだけ時間を送る**形にした。

| 物差し | 前の形 | 440 サイクル | 実機 |
|---|---|---|---|
| 1 パートぶんの設定（左右の差） | 79.0 | **61.1** | 61.4 ± 1.0 |
| 遅れて鳴る層の遅れ（24 音） | 1127.1 | **1135.6** | 1130.5 |
| 同・包絡の食い違い | 0.2991 | **0.2893** | — |
| 100 パフォーマンスの帯の差 | 0.584 | **0.560** | 0.216（実機どうし） |

**この追記の前半で「鍵の時刻が実機と標準偏差 3.6 サンプルで合う」と書いたものとは矛盾しない。**
あの測り方は録音の遅れを知らないので 1 次式で流れごと取り除いており、**一定のずれは
そこで吸収されている**。今回の形は 1 つ目のキーオンを 18 サンプル早めるが、それは
その一定のぶんに当たる。

**遅れて鳴る層を比べるときは、実機と同じ USB の口で流すこと**（`render --usb`）。
DIN で流すと 1 バイト 14.11 サンプル、USB なら約 1.9 サンプルで、届く時刻が変わる。
DIN で比べていたときは 440 の形が悪く見えていた。

440 という数の出どころ（チップの何かの周期なのか、BSC の設定なのか）は分かっていない。
1 サンプル 635 サイクルの 0.69 で、きれいな比にはならない。試験の指紋は焼き直した。

## 37. リバーブ RAM の地図の有効ビット（0x80e）が、読み書きに効いていない（直した）

**症状**: 音を伸ばしたままインサーションの種類をディレイ系（DELAY LCR・CROSS DELAY）や ENS DETUNE へ替えると、
替えた**遅延時間ぶん後に**全振幅に近いパルスが出て、それがディレイの繰り返しに乗って何度も鳴る（issue #8）。
信号の振幅 2500 に対してパルスは 28000。

読み込みの最中、MEG の 20 命令ほどが飽和値（0x7fffff）を 3 サンプルにわたって遅延メモリの同じ番地へ書いていた。
新しいプログラムと古い定数・番地表が混ざった状態を動かしているため。命令 64bit の 4 分割の書き込みを
最後の 1 つで揃えても消えない（定数と番地表は別に書かれる）。区画を 0 にする処理（0x80f）を止めても同じ。

**実機（XG モード、S/PDIF）**: 切り替えの間、出力は**ちょうど 0 が 163.8ms 続く**（3 回とも 7222・7194・7223 サンプル）。
そのあとにパルスは出ない。波形の最大の段差は信号の 1/5（120 対 600）。

firmware は種類を替えるとき、`revram enable`（0x80e、`100000 001110`。0 が有効、1 が無効）へその区画のビットを立て、
区画を消して（0x80f）、プログラムと定数を書き、最後にビットを落とす。こちら（と MAME）は
`m_revram_enable` を覚えるだけで読み書きに効かせていなかった。

直し方: MEG の遅延メモリの読み書きで、その番地が入る区画（地図の選び方は `resolve_address` と同じ）の
ビットが立っていたら、**書き込みは落とし、読み出しは 0 を返す**。命令表（`op`）に区画の番号を持たせ、
JIT も解釈実行も同じように見る。

直した後（同じ MIDI、切り替え 3 回）:

| | 出力の最大 | 8000 を超えたサンプル | 最大の段差 |
|---|---|---|---|
| 直す前 | 28812 | 81 | 28214 |
| この直し | 4424 | 0 | 1374 |

切り替えの前後の音は変わらない。同じ MIDI を実機（XG モード、S/PDIF）と鳴らし比べると、全体の音量差を除いた
1/3 オクターブ帯の食い違いは THRU 0.21dB、DELAY LCR 0.28dB、ENS DETUNE 0.31dB、CROSS DELAY 0.26dB（どれも最大 0.9dB 以内）。

**「実機はちょうど 0」は状態の違いだった（同じ晩に確かめ直した）**: 最初の録音で実機が 163ms ちょうど 0 になったのは、
そのとき実機の系リバーブが切れていて、鳴っていたのがインサーションを通る音だけだったため。エミュは
`--reset xg` の既定（HALL 1・送り 40）で鳴らしていたので、リバーブの尾が残って -12dB ほど聞こえていた。

MIDI の頭でリバーブを HALL 1・送り 40 と明に揃えて録り直すと、読み込み中の残りは
**実機 -11.8dB、エミュ -11.9dB**（普段の振幅に対する中央値）で一致する。波形の最大の段差も
普段の振幅に対して実機 0.72・エミュ 1.07。リバーブ・コーラス・バリエーションを全部切った MIDI では、
**実機もエミュも読み込み中の 6174 サンプルが全部ちょうど 0**。

鳴り終わった音の残響が残っている間に種類を替える試験でも、実機・エミュとも尾は切れずに滑らかに減る。
つまり firmware が黙らせるのはインサーションを通る道だけで、系のリバーブはそのまま続く。

MAME も `m_revram_enable` を使っていないので、同じパルスが出るはず。

MAME に投稿した PR（2026-09-16）: [mamedev/mame#16154](https://github.com/mamedev/mame/pull/16154)（ブランチ `swp30-revram-bank-enable`）。
MAME にはインタプリタと DRC の両方に同じメモリ処理があるので、両方で区画の有効ビットを見るようにした
（DRC は命令ごとに区画が決まるが、レジスタは実行中に変わるので、生成した機械語の中で毎回試す）。
区画を選ぶところは `resolve_address` と同じ選び方を `map_bank` に切り出した。

## 38. 三角波の音量の LFO が、音程と同じく中央から始まっている（直した。15 の訂正）

**症状**: 要素自身が音量の LFO（スロット 0x05 の下位 7bit が深さ）を持つ XG の変化音色で、鳴り始めの 0.1 秒が
実機より最大 6dB 小さかったり大きかったりする。0/21/38（要素 2 が深さ 0x18）は -3.8dB、0/69/90（両要素 0x10）は
-6.1dB、0/64/44（0x06）は +1.9dB。深さを持たない GM 版（0/0/38・0/0/44・0/0/90）は実機と合う。
実機で 2 回録っても同じ形、エミュの鳴らし始めを 2.5ms の刻みの中で 4 通りずらしても同じ形なので、揺れではない。

15 で、三角波はカウンタに 0x10000 を足して中央（0x800）から上がり始める形にした（Square Lead C5 のビブラートが
実機と 3 セント以内で重なる）。ところが `get_amplitude` も同じ `m_state` を使っていた。音程は `state - 0x800` なので
中央が「効きなし」だが、音量は `state * 深さ` を減衰に足すので 0 が「効きなし」で、中央から始めると
鳴り始めから深さの半分だけ音を下げていた。

直し方: 三角波（type 1）のときだけ、音量側はカウンタを足さずに作った三角波（一番下から上がる）を使う。
音程側は 15 のまま。

確かめ方: 音量側の始まりを 1/4 周期ずつ 4 通りにして、XG の変化音色 1225 種のうち実機と差の出た 116 種を実機で
2 回ずつ録ったものと比べた（頭 0.1 秒・0.1-0.5・0.5-1.0・離した後の 4 窓、1/3 オクターブ）。差の合計は
一番下から 272.8、中央から（直す前）325.3、一番上から 313.5、中央から下へ 306.8。一番下からで 0/21/38 3.8 → 0.0、
0/64/44 1.9 → 0.0、0/65/44 1.7 → 0.0、0/127/44 1.6 → 0.0、0/69/90 6.0 → 0.1、0/70/7 2.3 → 0.0dB。

ほかは悪くならない: 変化音色 1225 種で差 1.5dB 未満が 1109 → 1122、GM の 128 音（同じ晩に録り直した実機と）が
121 → 123、100 パフォーマンスの帯の食い違いの平均が 0.614 → 0.608dB。モジュレーションホイールで掛けるトレモロ
（パートの MW LFO AMod Depth）は firmware が音量を書き換えていてこの道を通らず、実機と 50ms ごとに 1dB 以内のまま。

鋸歯状波（type 0）は 15 で ChrchBel のトレモロが実機と合っていて、矩形波（type 2）とサンプル＆ホールドは
もともと 0 から始まるので変えていない。

こちらのコミット: d6de416（`swp30.cpp` の `lfo_block::get_amplitude`）

## 39. 遅延メモリへ書く値が負の無限大の側へ丸められ、音が止んでもリバーブが鳴り続ける（直した）

MEG が遅延メモリ（リバーブ RAM）へ書く値は `p >> 15`（算術シフト）で、負の値は負の無限大の側へ丸まる。
帰還のあるリバーブでは負の値が 0 に戻らず、入力が 0 になったあとも、リバーブが -100dB あたり（音の 50dB 下）で
数百 Hz の音を出し続けた（discussion #69 で、実機で鍵を離したあとの低い音として報告された）。レジスタへ書く値は
18 で 0 の側への切り捨てに直してあったが、メモリへの書き込みは別の道で、そのままだった。

`meg_mem_value`（`p / 32768`。0 の側へ）にした。JIT（x86・x64・ARM）も同じ。

確かめ方: GrandPno（リバーブの送り 40、HALL1 の既定）の C4 を 6 秒押して離し、実機を 32bit 浮動小数で録った
（`rec.exe --float`）。1-5 秒の平均で音量をそろえて 0.1 秒ごとに比べると、離して 0.6 秒後: 実機 -112.8、
直す前 -98.5、直した後 -110.5dB。0.8 秒後: -117.8 / -99.9 / -120.0。実機は 2.6 秒後にほぼ無音（-156dB）になり、
直す前は 10 秒たっても -103dB で鳴っていた（633・254・528Hz の山）。直した後は 1.0 秒後にぴったり 0。
（四捨五入も試した。実機との近さはほぼ同じで、レジスタと同じ 0 の側を採った）

ほかは変わらない: PHAZE1.MID の 60 秒で、50ms の帯の差の最大 0.1dB（消え際だけ）。

こちらのコミット: 6a18898（`swp30.cpp` の `meg_mem_value`、`swp30_jit.cpp`）

MAME に投稿した PR（2026-10-02）: [mamedev/mame#16293](https://github.com/mamedev/mame/pull/16293)（ブランチ `swp30-meg-memw-rounding`。解釈実行と DRC）。
MAME の `-nodrc` の有り無しの差（音の出だしで最大 363）は master にもとからあり、この直しとは関係ない。

## 40. フィルタ 1 の切る高さが、書いた値へすぐ飛ぶ（実機は 0x01 の上位の速さで滑る。直した）

スロットの `0x01` は MAME では「素通しの量」（`.xxx xxxx uuuu uuuu` の下位 8bit）とだけ読まれていて、上位 7bit は
どこからも使われていなかった。firmware はここに音の途中でも `0xDC`・`0xAA`・`0xC1` などを書く。

firmware の書き方（v2.01）: 10ms ごとに `0x00`（切る高さ）と組で書き、上位は
`表[0x1E58D6 + |今の切る高さ - 前の切る高さ| / 2] | 0x80`。表は 92, 42, 50, 54, 58, 60 … 86, 88 と、差 0 のところを
除いて**差の対数**で増える。上位 7bit を指数 4bit・仮数 3bit とみて `(8+m) << e` にすると、差に比例する（差 2・4・8・24・48 で
比 1.08・1.08・1.08・1.00・1.00）。つまり**次の 10ms のうちに行き先に着く速さ**を書いている。
CC74 で切る高さが大きく動いたときは、別の道（`0x12E74C` の前）で `0xC1`（65）を書く。

チップは書いた値へすぐ飛ばず、この速さで滑らせる、と読んだ。1 サンプルに `(8+m) << (e+2)` / 65536 単位
（切る高さは 3.8 の浮動小数の 11bit。上 4bit の形は滑らない）。鍵を押したときは滑らせずに書いてある値から始める。

確かめ方: 実機（USB の 1 番 → S/PDIF、`rec.exe --float`）に、レゾナンス最大（CC71=127）の音を鳴らして CC74 を
40↔100（大）・40↔52（小）と飛ばし、1 秒かけて 40→100 と上げた。エミュと標本単位でそろえ、区間ごとの差（実機の大きさに対する dB）:

| 区間 | 直す前 | `<< (e+1)` | **`<< (e+2)`** | `<< (e+3)` |
|---|---|---|---|---|
| Saw Lead（0,81）鍵 36・大きく上げる | -6.2 | -3.5 | **-14.0** | -6.1 |
| 同・大きく下げる | -6.8 | -4.2 | **-16.0** | -8.8 |
| 同・小さく上げる | -8.6 | -7.8 | **-23.8** | -10.1 |
| 同・小さく下げる | -10.2 | -8.2 | **-24.7** | -10.5 |
| 同・動かないところ（目安） | -25.9 | -25.9 | -25.9 | -25.9 |
| Synth Bass 1（0,38）鍵 48・小さく上げる | -4.1 | -7.8 | **-23.0** | -8.4 |
| 同・小さく下げる | -1.7 | 1.3 | **-16.7** | -2.3 |

`e+2` だけがはっきり当たる。大きく飛ばしたとき実機は約 120ms かけて上がり、`0xC1`・差 0x2FA で計算すると 123ms。
大きく飛ばしたところに残っていた -10〜-16dB は、滑り方の違いではなかった（2026-11-05 に詰めた）。

- **CC74 の届く時刻のずれ**: USB で送った CC は、実機には鍵を押した時刻から見て 1〜3ms 遅れて、しかも 1 つずつ違う遅れで届く。
  firmware は CC74 を 10ms の刻みを待たずにすぐ書くので、このずれがそのまま滑り始めのずれになる。エミュに送る CC74 を
  0.25ms 刻みでずらし、区間ごとに一番合う時刻をとると、Synth Bass 1（声が 1 つ）は大きく上げる -9.2 → **-35.8**、
  大きく下げる -4.1 → **-35.3**、小さく上げる -21.7 → -28.8、小さく下げる -15.3 → -27.0。
  動かないところ（-35dB）と同じところまで来る。2ms ずらした状態で速さを 0.94〜1.06 倍にすると、大きく下げるところと
  小さく動かすところはどれも悪くなる（大きく上げるところだけ 1.03 倍で少しよくなるが、時刻のずれと区別がつかない）。
  切る高さの代わりに係数 p1 を一直線に動かす形も試したが、合わない（-1dB 前後）。式 `(8+m) << (e+2)` はこのままでよい。
- **Saw Lead の止まっているところ**: 2 つ重ねた声の片方だけが、実機とずっと一定の小数サンプル（0.4〜0.85）ずれている。
  倍音の大きさは 0.0dB でそろっていて、ずれは時間で増えない（音の高さは合っている）。ずれの量は録るたびに変わるので、
  鍵を押した時刻と firmware の 10ms の刻みの位置関係（音の高さの包絡線の始まり）で決まるものと見ている。フィルタとは関係がない。
  切る高さが高いと高い倍音が多く出るので、このずれが差として大きく見えていた。
フィルタ 2（`0x02`）にも同じ仕組みがあった（41 番）。

ふだんの音への効きは小さい。包絡線で少しずつ動くとき（表の 42・60 など）は次の 10ms の書き込みより前に着くので、
段が 2〜3ms のなだらかな坂になるだけ。効くのは CC74 などで切る高さを大きく動かしたとき。

状態の保存: 滑っている途中の値は `filter_block` の外（`m_filter_cur`）に置き、状態の版を 16 にした。
`--native-engine` の声は鍵を押したときの `0xFFFF` のまま書き換えないので、今までどおりすぐ着く（滑らない）。

こちらのコミット: dd74bfd（`swp30.cpp` の `filter_block::step`・`keyon`、`m_filter_cur`、状態の版 16）

## 41. フィルタ 2 の切る高さも、書いた値へすぐ飛ぶ（実機は滑る。0 の行き先は 0x800 下。直した）

firmware が音の途中で `0x02` を書き換えるのは、パートの HPF（`0A pp 20`）を鳴らしたまま動かしたとき。
`0x02 = 0x8000 | clamp(byte82 * 16 + 24 * (HPF - 64), 0, 0x7FF)` をすぐ書く（10ms の刻みを待たない）。
`0x03` はいつも `0x5010` で、40 番と同じ読み方なら上 7bit は 80（指数 10・仮数 0）。HPF が 64 以下だと下 11bit は 0 で、
MAME ではフィルタ 2 がまるごと素通しになる。

実機（Saw Lead（0,81）鍵 48、USB の 1 番 → S/PDIF、`rec.exe --float`）で HPF を振って録り、450Hz より下の
大きさの時間の変わり方（2ms ごと）をエミュと比べた。位相の差（40 番の Saw Lead の 2 つの声のずれ）に左右されない比べ方。
HPF の SysEx と同じ時刻にドラムを鳴らして目印にしたところ、実機に届く遅れは 1ms 未満だった。わかったこと:

- **滑る**。0 を挟まない動き（HPF 0x41 ↔ 0x7F = 切る高さ 0x018 ↔ 0x5E8、0x41 ↔ 0x60）で速さを振ると、
  40 番の式の **1.5 倍**（1 サンプルに 0.75 単位）が一番合う（1.44 倍もほぼ同じ。1.25 倍・2 倍ははっきり悪い）。
  `0x03` に書かれる値が 1 つだけなので、式のどこが 1.5 倍なのかは決められない。
- **0 の行き先は 0x800 下**。HPF を 64 以下（切る高さ 0）から上げると、実機は約 60ms 何も変わらず、そのあと素早く変わる。
  行き先を 0 にすると早すぎ、0x800（2048）下に置くと、0 にしておいた長さ（300ms・700ms・1000ms・鍵を押したまま）によらず合う。
  0x780 ははっきり悪く、0x880 も合わせると悪い。下げるときも 0 で止めず 0x800 下まで行かせた（0 を割ったところで
  素通しになるので音には出ない。0 にしてから 60ms 以内に上げたときだけ違いが出るが、そこは確かめていない）。
- 0 より下にいるあいだは素通し（切る高さ 0 のフィルタを回し続ける形よりよく合う）。

| 平均の差（dB、450Hz 以下の大きさの差の平均） | 直す前 | 直した後 |
|---|---|---|
| 0x018 → 0x5E8（上げる） | 6.32 | **0.62** |
| 0x5E8 → 0x018（下げる） | 3.95 | **0.22** |
| 0x018 → 0x5E8（2 回目） | 6.15 | **0.10** |
| 0x5E8 → 0x018（2 回目） | 3.35 | **0.31** |
| 0 → 0x5E8（0 にして 300ms） | 21.78 | **0.64** |
| 0x5E8 → 0 | 2.60 | **0.20** |
| 0 → 0x300（0 にして 1000ms） | 1.81 | **0.03** |
| 0 → 0x300（0 にして 300ms） | 2.11 | **0.09** |
| 別の録音: 0 → 0x5E8（鍵を押して 1 秒） | 21.74 | **0.62** |
| 同: 0x5E8 → 0 | 3.64 | **0.65** |

効くのは、鳴らしたまま HPF を動かしたときだけ。鍵を押したときは滑らせずに書いてある値から始める（0 なら 0x800 下から）。

状態の保存: 滑っている途中の値は `m_filter2_cur`（符号つき、`<< 16`）に置き、状態の版を 17 にした。

**MAME にまだ入っていないもの**（2026-10-02 に master 3f748f459d と突き合わせた）: 1（sh_port の m_dr）・2・4・6・7・8・9・11・13・14・15・16・25・27・28・29・31・32・38。
11・29・31 は `swp30-meg-branches`、32 は `swp30-meg-index2`、25 は `swp30-meg-lfo-phase`（fork にある。25 はそのまま載る）。36 は出さない。

## RS7000（SWP30B）での発見と、MU2000 での確かめ（2026-10-22。取り込まなかった）

sneak-thief さんの RS7000 のエミュレーター（RS7007。discussion #162）は、このコアを取り込んで、RS7000 の実機の録音に合わせた
直しを 8 つ足している。MU2000 にも当てはまるかを、MU2000 のファームの書き込み（`WTRACE`）と、このコアの今の作りで確かめた。
**どれも MU2000 には当てはまらないか、確かめられないので、取り込んでいない。**

| RS7000 の直し | MU2000 で見たこと | 判断 |
|---|---|---|
| ボイスの EQ（0x20-0x2A）を 2 次の 1 段（b0 = 0x24、b1 = 0x20、b2 = 0x22、a1 = 0x26、a2 = 0x28、0x2A は使わない）と読む | MU2000 のファームは EQ を平らにするとき 0x20 = e05d、0x22 = 1fa3、0x24 = 2000、0x26 = 0257、0x28 = fda9、**0x2A = 2000** を書き、パートの EQ を動かすと 0x2A も変える。今の読み（1 次 2 段）だと、どちらの段も極と零が打ち消し合って**ぴったり平ら**になる。2 次の 1 段と読むと、平らのはずの設定で高域が +8.3dB 持ち上がる | 今の読みのまま |
| ピッチ EG の読み戻し（内部ポート 4）の下 14bit を「0x2000 が 0」の形にする（モノのパートのポルタメント） | MU2000 のファームは bit 14（目標に着いたか）しか見ない（`internal_r` の注記、0x12B81C） | 関係しない |
| フィルターのモード 3・7・b・f をレゾナンス付きの Chamberlin 型にし、2 段目を入力から取って和にする。モード e の 2 段目の二重のシフト | GM の 128 音色を鳴らすと、MU2000 が使うモードは 1 段目が 1（レゾナンス付きの LPF）、2 段目が 8（HPF）だけ。3・7・b・e・f は出てこない | 関係しない |
| フィルターの出力の頭打ちを ±2²³ に広げる | 強いレゾナンスで MU2000 の実機と比べていない | 実機で確かめるまで今のまま |
| カットオフの係数を 2k² にし、仮数を指数の側へ 3 分の 1 曲げる | このコアのフィルターは MU2000 の実機とよく合っている | 取り込まない |
| LFO の速さの bit 13 を「×8 の範囲」と読む | MU2000EX の実機で、ビブラートの速さ 76 が `0x66xx` = 6 番目のビットを含む 38 段 = 6.43Hz（4 番） | 取り込まない（SWP30 と SWP30B の違いかもしれない） |

確かめ方: `WTRACE=<サンプル>` を付けて `render.exe` で鳴らし、標準エラーの書き込みの記録から、スロット 0x00・0x02 の上の 4bit と 0x20-0x2A の値を数えた。
